I'm a video editor learning to build things with code. That sentence still feels a little strange to write. For a long time, “making something” meant footage, a timeline, layers, masks, and a final export. Now it can mean asking an AI tool for help, opening a project in Cursor or Claude Code, and trying to understand what the files are doing before I change them.

One thing that helps is thinking about code like an edit.

A timeline isn't the footage. It's a set of decisions about the footage: what goes first, what stays, what gets layered on top, where the cut happens, and how one moment hands off to the next. The viewer sees a finished sequence. Underneath it is an arrangement that can be adjusted without changing the original clips.

Code has that same separation between the thing and the decisions that assemble it. A page on a website looks like one object. But it might be made from a layout, a component, data, styles, and a route that tells the browser where to find it. When I change one of those pieces, I am changing a decision in the construction of the page. I don't need to think of the whole site as one giant block.

That is reassuring when you're new. A codebase can look like a wall of syntax, and the first impulse is to treat it as one mysterious machine. Editing has taught me that a complicated result can be made of smaller, understandable parts. Find the piece you're trying to change. Understand what it connects to. Make one adjustment. See what the new version does.

The analogy isn't perfect. A timeline lets me see and hear the result almost immediately. Code has rules that aren't visible in the finished page. One missing character can stop an entire build; one small change can affect something that seems unrelated. Editing has trained my eye for sequence and layers, but it hasn't made me a programmer by osmosis.

The other lesson it gives me is to keep the original safe. In a video project, the source footage is still there when I trim a clip or change the grade. I can try something, decide it doesn't work, and go back. That non-destructive habit is useful in code too. Make a small change. Keep track of what changed. Check the result before stacking five more guesses on top of the first one.

AI makes that habit more important, not less. It can help me move through unfamiliar files and explain a concept in plain language. It can also suggest a confident change that I don't yet understand. If I accept a whole pile of edits at once, I lose the ability to tell which decision helped and which one introduced a problem. The tool can produce the cut. I still have to watch it back.

There's a difference between getting something to work and learning how it works. Sometimes the useful next step is not asking for more code. It's asking what this file is responsible for, what will change if I edit it, or how to undo the last move. That's like opening a sequence and tracing where a shot came from before rearranging the whole scene.

I am still learning this. I don't want to pretend I have crossed some finish line where code stopped being foreign. The point of the editing comparison is not that I already know the answer. It's that I have a way to stay curious instead of getting intimidated by the scale of the thing.

When I open a project now, I try to remember what a timeline taught me: a finished experience is often an arrangement of smaller choices. You don't have to understand every possible choice before you make the next one. You do have to know what you changed, look at what happened, and be willing to revise.

That feels like a good way to learn almost anything. Start with the smallest useful cut. Keep the source. Watch the result. Then decide what comes next.
